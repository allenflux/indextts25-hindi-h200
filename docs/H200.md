# 外部社区路线：H200参考runbook

原生路线见 [NATIVE.md](NATIVE.md)，不需要社区后端许可。本页只针对外部社区接口。

本页是操作计划，**没有在 H200 上执行**。本项目工具不自动 SSH、开机、申请 GPU 或下载模型。所有 GPU 步骤由你在自己的已授权机器执行。先固定计划、过 gate，再扩大数据；不要预估或承诺 GPU 小时。

## 环境与许可证

在 H200 Linux 机器上选择实际持久数据盘的隔离目录，以下变量必须由你填写，不能直接复制占位路径：

```bash
export HI_H200_WORK=/your/real/data-volume/hindi-work
export PREP="$HI_H200_WORK/indextts25-hindi-h200"
export OFFICIAL="$HI_H200_WORK/external/index-tts"
export BACKEND="$HI_H200_WORK/external/index-tts-2.5-ft"
export MODEL="$HI_H200_WORK/weights/indextts25"
export AUDIO="$HI_H200_WORK/data/authorized-audio"
cd "$PREP"
source scripts/environment.sh
export PYTHONPATH="$PREP/src"
```

先确认这些路径在真实挂载上。原始模型目录之后只读使用；data/features/runs/cache 均放在同一隔离工作目录。不要覆盖现有项目。

需要 NVIDIA 驱动与兼容 CUDA 工具链、Python **3.11**、git、uv，以及已经人工处理好的模型/数据/后端权限。上游支持的 Python 是 >=3.10,<3.12；CPU 工具的 3.13 验证不代表 GPU 依赖支持 3.13。社区后端没有 LICENSE，先取得明确许可或换用有合适许可的兼容实现；源预检只接受锁定版本，换后端必须重新审计。

源目录分别 checkout 到 `upstream.lock.json` 的完整 SHA。只读先检查：

```bash
python3 scripts/check_backend.py --official-repo "$OFFICIAL" --backend-repo "$BACKEND" --source-only
```

这个命令不 import 后端、不加载模型，成功也会写 `ready_for_training: false`。不得把它当成后端成功运行。

授权后才在官方环境安装依赖。官方 `uv.lock` 已锁部分依赖；社区 requirements 不是完整 transitive lock。以下选择不安装可选 all-extras，避免把不支持的加速路径带进实验；这是基于官方 pyproject 的安装选择，本项目未实跑：

```bash
cd "$OFFICIAL"
uv sync --frozen --python 3.11
uv pip install --python "$OFFICIAL/.venv/bin/python" -r "$BACKEND/requirements.txt"
export GPU_PY="$OFFICIAL/.venv/bin/python"
mkdir -p "$HI_H200_WORK/reports"
uv pip freeze --python "$GPU_PY" > "$HI_H200_WORK/reports/gpu-requirements-resolved.txt"
uv --version > "$HI_H200_WORK/reports/uv-version.txt"
"$GPU_PY" --version
cd "$PREP"
```

保留安装命令、包哈希/wheel来源、官方 uv.lock 哈希与 GPU 容器镜像 digest（若使用）。官方固定 torch/torchaudio2.8.*、transformers4.52.1、numpy2.2.6；这些只是上游约束，不等于本仓库验证过其 H200 组合。运行 `nvidia-smi`、保存驱动、CUDA、GPU 型号/实际容量与 BF16 可用性；本次会话未执行这些命令。只使用单 GPU，不启用 use_accel、DeepSpeed 或未验证的 flash-attn 路径。

在本地创建被忽略的授权记录与模型哈希清单（以下是 schema，**必须填真实值，不能照抄为授权证明**）：

```json
{"backend_commit":"abdcbda0f6624d87134da8d1f4d482edac4a2fb9","permission_confirmed":true,"permission_basis":"你已取得的明确授权文件位置和适用范围"}
```

```json
{"repository":"IndexTeam/IndexTTS-2.5","snapshot_revision":"实际模型snapshot的40位commit","files":{"config.yaml":"64位sha256","gpt.pth":"64位sha256","codec.pth":"64位sha256","multilingual_zh_ja_yue_char_del.tiktoken":"64位sha256"}}
```

把实际所有模型文件（含辅助模型）纳入 files 并独立核验来源。最低文件清单不保证完整加载；不要为了过检查填虚假 revision。将记录保存为 `$HI_H200_WORK/rights.json` 与 `$HI_H200_WORK/weights.json` 后：

```bash
python3 scripts/check_backend.py --official-repo "$OFFICIAL" --backend-repo "$BACKEND" --model-dir "$MODEL" --rights-record "$HI_H200_WORK/rights.json" --weight-manifest "$HI_H200_WORK/weights.json"
```

加载前设置 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1` 并在受控离线环境验证，阻止缺失辅助资产被悄悄下载。必须另外执行真实 `check_setup.py --repo "$OFFICIAL" --model-dir "$MODEL" --lang hi --normalizer none --case none`，准备 Hindi 纯文本文件后可加 `--sample-text FILE`；`--load-model` 才尝试真实模型加载。该动作需你在 GPU 环境执行，可能因缺失依赖、辅助模型或不兼容报错；错误是继续训练的阻塞。

## 数据和独立特征提取

准备自己的语料，先人工听检、去除重叠片段，合并同一人的 speaker ID，至少十位 speaker 的 val/test 才适合做正式泛化评测。先用 train split 的 16–64 条短语音过拟合，保留 speaker 隔离验证。不要用合成 tone demo 训练。

```bash
python3 -m hi_h200 prepare "$HI_H200_WORK/data/input.jsonl" --audio-root "$AUDIO" --output "$HI_H200_WORK/prepared"
python3 -m hi_h200 validate "$HI_H200_WORK/prepared" --audio-root "$AUDIO"
```

每次改变文字、模型、前端或音频，都用新的 feature 目录。先从 train speaker 中另建过拟合小集合对应的 prepared 目录；保持至少三个 speaker，并确保 train 至少16个目标（batch2×accum8），否则后端可能在每个 epoch 不足一次累积而零更新。以下对三个已有 split 分别提取；正式 run 和 overfit run 应使用不同的 prepared/features/runs 目录：

```bash
for split in train val test; do
  "$GPU_PY" "$BACKEND/scripts/preprocess.py"     --repo "$OFFICIAL" --model-dir "$MODEL"     --manifest "$HI_H200_WORK/prepared/backend_${split}.jsonl"     --output-dir "$HI_H200_WORK/features/${split}"     --lang hi --normalizer none --case none --no-pronunciation     --device cuda --min-seconds 1 --max-seconds 20 --max-ref-seconds 15     --val-size 0 --val-speakers 0 --seed 1234
done
```

每个目录都输出 `utterances_train.jsonl`，名称不表示 split。检查每个 `preprocess_stats.json`：首次权威提取 cached_reuse=0，failures/各类 skipped=0，processed 等于该 split 的源条目数。进程退出0不能代替完整性检查；不要使用 --limit 做正式权威提取。

生成每个目标一条同 speaker 不同 clip 的配对。`--max-ref-seconds 15` 裁剪提取 speaker/emotion conditioning 的参考波形，不把20秒目标codes剪成15秒；prompt使用该conditioning。此处 120/1728/640 是短语音实验的**显式筛选策略**，不是官方容量；模型容量上限须以实际 config 为准，超限失败后审查、重建小集合，不要只抬高数值：

```bash
for split in train val test; do
  python3 -m hi_h200 pairs "$HI_H200_WORK/features/${split}/utterances_train.jsonl"     --prepared "$HI_H200_WORK/prepared" --audio-root "$AUDIO" --split "$split"     --feature-root "$HI_H200_WORK/features/${split}"     --output "$HI_H200_WORK/features/${split}/pairs.jsonl"     --max-text-tokens 120 --max-code-tokens 1728 --max-prompt-code-tokens 640
done
```

CPU 配对核查 ID 全集、原始数据哈希、speaker/语言/文字/路径与长度元数据；不假装读取了 NPZ。接着必须在装有 NumPy 的后端环境执行 `scripts/check_features.py`，验证全部实际数组、元数据长度、token 范围和 exact frontend 编码，并生成与 pair 清单及特征哈希绑定的审计报告。详见该脚本 `--help`；没有完整前端一致性的报告，配置生成器应拒绝继续。Hindi embedding 索引17不是 `<|hi|>` 的数值 token ID。

下面示例的 vocab/codebook/dim 来自公开2.5配置，必须与你实际锁定 snapshot 一致；完整 gate 会读取真实 config.yaml，不一致即失败。120/1728/640 与前述配对筛选一致，只能比模型容量更严格。

```bash
for split in train val test; do
  "$GPU_PY" scripts/check_features.py \
    --manifest "$HI_H200_WORK/features/${split}/utterances_train.jsonl" \
    --pairs "$HI_H200_WORK/features/${split}/pairs.jsonl" \
    --feature-root "$HI_H200_WORK/features/${split}" \
    --prepared "$HI_H200_WORK/prepared" --audio-root "$AUDIO" --split "$split" \
    --number-text-tokens 60509 --max-text-tokens 120 --max-code-tokens 1728 \
    --max-prompt-code-tokens 640 --codebook-size 8192 --emotion-dim 1280 \
    --official-repo "$OFFICIAL" --backend-repo "$BACKEND" --model-dir "$MODEL" \
    --rights-record "$HI_H200_WORK/rights.json" --weight-manifest "$HI_H200_WORK/weights.json" \
    --output "$HI_H200_WORK/reports/${split}.feature-audit.json"
done
```

`--structural-only` 不 import 后端，仅供排查数组，报告不会被配置生成器接受。上述完整 gate 使用真实词表离线复算全部文本，不调用 GPU；它在本次会话没有运行，CPU 单元测试中只使用模拟 frontend。


## 配置、过拟合与 100-step smoke

`configs/hindi-h200.example.json` 是原创实验起点：LoRA rank16/alpha32，BF16，microbatch2、梯度累积8、学习率5e-5，目标语言/文本行与 heads 开启，声学后端冻结。名义有效 batch16，不保证吞吐或显存占用。heads 同时包含 mel_head 和 text_head；导出风险见评测文档。

先用 `scripts/render_backend_config.py --help` 的完整参数渲染 `--profile overfit` 配置（300 次 optimizer 更新上限），通过小样本 gate 后再用新目录渲染 `--profile smoke`（100 次 optimizer 更新）。它只生成配置，不执行训练；未知参数、错误 source commit、欠缺授权/权重/特征审计会明确失败。`--train-pairs` 与 `--val-pairs` 必须分别来自独立 speaker split，test 不传入训练器。

```bash
mkdir -p "$HI_H200_WORK/runs"
# 先设 overfit，完成小样本验收后再改为 smoke；输出必须是新文件/新run目录。
PROFILE=overfit
python3 scripts/render_backend_config.py \
  --official-repo "$OFFICIAL" --backend-repo "$BACKEND" --model-dir "$MODEL" \
  --rights-record "$HI_H200_WORK/rights.json" --weight-manifest "$HI_H200_WORK/weights.json" \
  --train-pairs "$HI_H200_WORK/features/train/pairs.jsonl" \
  --val-pairs "$HI_H200_WORK/features/val/pairs.jsonl" \
  --train-feature-report "$HI_H200_WORK/reports/train.feature-audit.json" \
  --val-feature-report "$HI_H200_WORK/reports/val.feature-audit.json" \
  --profile "$PROFILE" --output-dir "$HI_H200_WORK/runs/hi-${PROFILE}" \
  --output "$HI_H200_WORK/runs/hi-${PROFILE}.json"
```

生成后训练命令中的 config/output-dir 必须使用同一 PROFILE；以下 smoke 示例只在 overfit gate 通过并且 smoke 配置已重新生成后执行。smoke 的数据长度分布应代表计划使用的训练批次；短样本结果不能直接外推全长语料。


渲染完成后实际入口是已核实的社区命令，**即使配置内含 output_dir，也必须重复传 CLI 的 --output-dir**：

```bash
# 先在另一个终端采样设备显存；输出目录需已创建。
python3 scripts/monitor_gpu.py --gpu 0 --interval 1 --samples 3600 --output "$HI_H200_WORK/reports/smoke-gpu.csv"
# 训练终端：先完成 overfit gate，再独立执行 smoke。
"$GPU_PY" "$BACKEND/scripts/train.py" --config "$HI_H200_WORK/runs/hi-smoke.json" --output-dir "$HI_H200_WORK/runs/hi-smoke"
```

监控器采集设备级显存/利用率，不能代替 `torch.cuda.max_memory_allocated()` 的分配器峰值，也不证明训练成功。结束训练后停止监控即可。实际 smoke 要确认最终 checkpoint 的 global step 恰为100（max_steps 数的是 optimizer 更新，不是 microbatch）；足够 epoch/每 epoch 可累积 batch 是必要条件。不要 resume 旧 run 冒充100步。

记录前20步预热、后80步稳定窗口：optimizer updates/s、log_interval=1 下 it/s 的 P50/P95（取倒数只能得到含训练/验证/保存开销的区间时间）、完整 wall time、OOM、非有限 loss、设备显存采样最大值；若需要精确 CUDA allocator 峰值，须在有许可的后端加入显式 reset/synchronize/peak instrumentation 后重新锁定审计。原生 it/s 包含上一日志以来的验证/checkpoint等开销，不是纯 kernel 时间。

要报告 samples/s 或 audio_seconds/s，必须根据**实际被消费的每个 batch**计数和时长求和，并除以相同稳定窗口 wall time；不能用全数据集总时长或 microbatch 数直接套算。后端没有原生这些指标，未加计数前留空，不伪造吞吐。TensorBoard 路径为 run/logs，观察 train/loss、train/text_loss、train/mel_loss、train/mel_top1、train/lr 和周期 val/loss 等。

| 记录项 | overfit | 100-step smoke |
|---|---|---|
| source/model/env/config/data hash | 未填 | 未填 |
| 实际 optimizer 更新数 | 未测 | 未测 |
| 稳定窗口 updates/s、区间时间P50/P95 | 未测 | 未测 |
| 显存采样最大值 / CUDA allocator峰值 | 未测 | 未测 |
| OOM/NaN/空音频/重复/截断 | 未测 | 未测 |
| 固定 prompt/seed 生成与试听 | 未测 | 未测 |

任何 gate 失败先定位数据、Hindi 前端、token 范围、冻结/梯度和导出问题。过拟合成功后才能扩大数据；100-step 成功后也不代表 Hindi 质量达标，仍须完整 held-out 与旧语言评测。原始模型永不覆盖；Hindi、其他语言 adapter 各自版本保存，用隔离进程加载，保留回滚路径。

共享 pod 运行前必须遵守 [中断与恢复方案](INTERRUPTION.md)，先完成真实 STOP/恢复演练；仅凭最终 checkpoint 存在不能宣称恢复可用。
